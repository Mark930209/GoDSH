# DeepSeek Harness 会话处理内部机制

> 从真实会话日志、诊断日志和 app.asar 源码核对出来的 DSH 会话层事实。做缓存、做插件、
> 做会话修复都需要这些。缓存实验本身见 [prompt-cache-investigation.md](prompt-cache-investigation.md)。

## 1. 会话日志：位置与存储格式

```
~\.dsh\sessions\--<workspace-slug>--\<sessionId>\session.v4.jsonl.zstd
```

- workspace slug 由路径转义而成，例如 `E:\Projects\DSH_Plugins_Dev` → `--E-Projects-DSH_Plugins_Dev--`。
- v4 日志是**拼接的 zstd 帧**（不是单个 zstd 流）：每次 flush 产一帧，帧 magic 为
  `28 B5 2F FD`，每帧含 1–18 行 JSON，帧尾有换行。
- **逐帧独立解压**：扫描 magic 找帧边界，对每帧单独 `zlib.zstdDecompressSync`。一个坏帧
  只污染它自己，其余帧照常读——所有分析脚本都这样处理。
- 装载器对撕裂的尾帧有容忍（返回其起点用于修复）。
- 帧内有行号全局偏移；修一行 = 定位所在帧、解压、改行、重压缩（写回时要带 checksum 标志
  以与写方一致）。

### 真实修复案例（session-a9ab6bf4）

装载报错 `SessionFormatError: llm/retry skips its policy attempt sequence`：超时重试链在
turn 27 step 15 处中断后，新链的 `retry` 序号从 1 重新开始，与前一链不连续。修复方法：
逐帧解压，把后一链的 `llm/retry` / `llm/retry-started` 事件里的 `retry` 序号整体加偏移
（1..6 → 7..12），保持与 `retryId`、`policyKey`（如 `auto-retry`）配对，重压缩写回。
**结论：retry 计数必须在同一 policy 链内单调连续，手写/修补日志时最易踩。**

## 2. 事件类型（按单会话中出现的字典序）

`agent-preset/selected`, `agent/inbox/spliced`, `approval/policy`, `assistant/attempt`,
`assistant/message`, `compaction/end`, `compaction/prune`, `compaction/start`,
`compaction/summary`, `job/registered`, `job/settled`, `llm/retry`, `llm/retry-started`,
`model/selection`, `permission/preset`, `request/context`, `request/header`,
`sandbox/mode`, `session`, `session/end-seed`, `session/title`,
`session/title-llm-request`, `step/end`, `system/message`, `todo/write`,
`tool/call`, `tool/result`, `turn/end`, `turn/start`, `user/message`, `workspace/changes`

要点：

- **`assistant/message` 是命中率对账的唯一事实源**。结构：
  `data.turn`、`data.step`、`data.usage{inputTokens,outputTokens,totalTokens,cacheReadTokens,...}`、
  `data.message.content[]`（块类型 `reasoning | text | tool-call`）、
  `data.source{kind:'model', provider, model, replayState}`；顶层 `e.time` 为 epoch ms。
  `tool/call`、`tool/result` 是工具调用的独立事件镜像，`assistant/message` 里也有对应块。
- **usage 字段名必须精确**：运行时 `tokenUsage` 投影按 `inputTokens / outputTokens /
  totalTokens / cacheReadTokens / cacheWriteTokens / reasoningTokens` 读取；写成
  `input/output/cacheRead` 之类会让投影出 `NaN`，**整条会话历史加载失败**
  （`failed to project session ... expected number, received NaN`）。写自定义 LLM 适配层时
  这是硬约束。
- `user/message` 的 `data.source.kind` 区分来源：`user`（真人，带 `rpcId`、
  `clientTimeZone`）、`time-context`（见下节）。
- `compaction/*`：压缩轮会 `prune` 历史再注入 `summary`——**压缩会重写前缀，压缩后第一
  个请求吃一次全价属于预期**。
- `model/selection`：用户显式选模后，路由会发布为 prompt variables（见 §4）。

## 3. 时间提醒与"模型已切换"提醒：都在末尾，不破前缀

- 时间提醒是一条**独立的末尾 `user/message`**，`source.kind:'time-context'`、
  `form:'snapshot'`，内容形如 `Time sampled while preparing turn N, step M: ...` +
  `Browser time zone ...` + `Elapsed since ...`。它作为独立消息追加，**不修改任何既有消息**，
  因此对前缀缓存无害（已实测前缀哈希恒定）。
- 切换模型时同样以追加的 user 文本出现：`[model changed: assistant turns above this point
  were generated by <provider>/<model>; ...]`。也是末尾追加，不破前缀。
- 推论：DSH 的上下文增长是 append-only 的，这正是命中率能稳在 94–99% 的结构性原因；
  插件/自定义层若往消息**中间**注入内容（工具目录、时间戳、状态块），就会破坏这个性质——
  目录只能进系统提示词末尾，这就是那套"目录进 system"设计的原始动机（尽管实验证明该网关
  下 `tools` 字段本身也不再挡缓存，见调查文档）。

## 4. LLM 水位（waterfall）钩子：能拿到什么、拿不到什么

DSH 的插件挂点是 waterfall：`ctx.waterfall(owner, name, payload, next)`，监听器
`(payload, next) => result`，返回 `next()` 或替换后的值。

### `system-prompt/assemble`

- 签名 `(assembly, context, next)`。`context.agent.id` **可用**（按 agent 区分主会话/子
  agent/skill），`context.agent.session.requestHeader()?.config` 是路由的兜底来源，
  `context.agent.options.provider/model` 再兜底。
- `assembly.variables.provider/model` **只在用户显式选过模型之后**才存在；默认模型会话
  没有这两个变量——判断路由时按 `variables → requestHeader → agent.options` 顺序取。
- `assembly.tools` 可清空（适配器就不再发 `tools`），`assembly.sections` 可追加自定义
  section（`interpolate:false` 防模板语法冲突）。单会话实测约 23 个 section。
- 同一回合该钩子会被**进入多次**（scoped/root 两种 via 各一次），做统计时注意去重口径。

### `llm/stream`

- 权威漏斗（asar 源码原文）：

  ```js
  streamWithRegistration(options, prepared) {
    return this.ctx.waterfall(this, "llm/stream", options, () => this.adapterStream(options, prepared));
  }
  ```

- 监听器签名 **只有 `(options, next)`，没有 agent/context 对象**。options 携带
  `provider / model / tools / messages / sessionId`；**子 agent 的请求 `sessionId` 为空**。
  因此任何按会话/agent 隔离的每路由状态，在这里唯一可用的隔离维度是 `options.sessionId`。
  这是实测出来的硬边界，别指望后续版本给第三个参数。
- `Object.isFrozen(request)` 可能是 true；冻结请求只能复制改写（`{...request, tools: []}`），
  原地改会静默失败或抛错。
- **事故教训：出站改写与入站解析必须绑在一起**。改写（剥 `tools`）挂在运行时补丁上、
  解析回复挂在 `llm/stream` 监听器上，两者一旦脱钩（监听器先被 dispose、补丁恢复失败被
  `try/catch` 静默吞掉），就变成"工具被剥掉、没人解析回复"的最坏状态：模型吐出协议文本，
  原样进正文，整轮没有工具执行。规则：**改写谁剥的工具，谁就必须负责解析回复**；卸载时
  第一步先解除补丁生效标志，让遗留补丁退化为纯透传。验证方法：诊断日志里
  `llm:rewrite` 与 `stream` 必须 1:1 配对，出现孤儿即脱钩。

## 5. 配置与凭据位置

- profile 补丁行：`~\.dsh\profiles\desktop\cordis.patch.yml`（`cordis.yml` 只放 `[]`；
  插件的 `config` 写在 patch 行里）。
- 凭据：`~\.dsh\.credentials.yaml`（如 `N1N_API_KEY`）。模型 profile 支持
  `cacheRetention`、`compat.*`（`sendSessionAffinityHeaders`、`sessionAffinityFormat`、
  `supportsLongCacheRetention`）——但对 `llm-api.net` 这些全部无效，见调查文档 §5。
- app.asar：`<安装目录>\resources\app.asar`（约 213 MB）。安装目录名会被 harness 改名，
  必须 `readdirSync` 动态解析。asar 是文本+二进制混合，用 latin1 读全文再定位关键字
  （`scripts/_asar_grep.mjs` / `_asar_slice.mjs`）。
- 适配器只在 `baseUrl` 含 `api.openai.com`，或 `cacheRetention==='long' &&
  supportsLongCacheRetention` 时发 `prompt_cache_key`——第三方网关默认不发。

## 6. 观测建议

- 想在生产会话上核对命中率：直接解会话日志打表（`scripts/_steps_usage.mjs`），不需要
  插件在场。
- 想做插件级诊断（前缀哈希、catHash、钩子配对）：在插件里往 `%TEMP%\<name>-diag.jsonl`
  追加 JSON 行，字段自定（曾用的有效字段：`t、hook、ok、tools、dropped、catHash、catLen、
  prefixHash、sessionId、downgraded、sysHasCatalog、messageCount`）。注意判"正文是否含
  某字面量"时先剔除代码块，否则正常提及会污染统计。
